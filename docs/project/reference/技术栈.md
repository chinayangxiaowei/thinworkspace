# 技术栈

**适用范围：ThinWorkspace Phase 0 / Phase 1**

**主语言：Rust｜首发平台：macOS＋APFS｜产品形态：单机 CLI**

Rust 是 ThinWorkspace 自身的实现语言，不是被管理工作区的语言限制；本文件中的 Cargo 命令用于本仓库研发，不构成产品对用户工具链的配置要求。

Phase 1 的首发技术目标是 macOS＋APFS；当前对用户承诺的 CPU、系统和 Git 资格组合只由 Phase 1 用户操作手册维护。底层能力历史起点不自动进入产品支持矩阵。

---

## 一、选型原则

Phase 1 技术选型遵循以下约束：

1. 一个本机 CLI，不引入常驻服务、HTTP、消息队列和异步运行时。
2. 核心业务逻辑不直接依赖 macOS、APFS 或具体系统调用。
3. 平台差异通过窄 Port 和 Adapter 隔离。
4. Git 仅通过系统 CLI 按需只读检查，不参与创建或自动交付。
5. SQLite 与文件系统生命周期通过 operation/Receipt 幂等恢复；不创建 Git 写事务。
6. 默认要求 CoW；只有用户显式使用 `--allow-copy` 才能完整复制。
7. 所有真实依赖版本由 `rust-toolchain.toml` 和 `Cargo.lock` 固定；本文不把易过期的 crate 小版本写成长期架构约束。

## 三、Phase 1 运行模型

Phase 1 选择同步命令模型：CLI 调用 Application Use Case，Application 通过 Port 同步调用 Git、文件系统、SQLite 和外部占用探测。GitInspector 内部启动系统 Git；用户开发命令不经过平台。并发来自多个 CLI 进程，不是单进程内的大量异步任务。

因此 Phase 1 不引入 Tokio 或其他异步运行时。这降低文件句柄、锁、过渡状态和崩溃恢复的审计复杂度。当 Phase 3 真正引入远程 I/O 时，再仅在远程模块评估异步运行时。

单机锁、查询/写入边界、operation/Receipt 和外部占用检查由[《Phase 1 单机 CLI 详细设计》](../design/ThinWorkspace_Phase1单机CLI详细设计_v1.0.md)管理，不在技术选型文档复制。

## 四、代码分层与 crate

```text
crates/
├── thinws-cli/
├── thinws-core/
├── thinws-application/
├── thinws-ports/
├── thinws-adapter-git-cli/
├── thinws-adapter-macos/
└── thinws-metadata-sqlite/
```

依赖方向：

```text
thinws-cli
    ↓
thinws-application
    ├──→ thinws-core
    └──→ thinws-ports
              ↑
              ├── thinws-adapter-git-cli
              ├── thinws-adapter-macos
              └── thinws-metadata-sqlite
```

### 4.1 thinws-core

包含 Phase 1 详细设计和跨平台物化设计定义的纯领域对象、状态、策略、证据与错误类型，不包含 CLI renderer 或平台实现。具体对象和字段不在技术栈重复。

不得依赖：

- `std::process::Command`；
- macOS/Linux 条件分支；
- SQLite；
- Git CLI；
- 具体文件系统路径布局实现。

### 4.2 thinws-application

负责按 Phase 1 详细设计编排用户手册中的用例及其幂等恢复，不包含平台系统调用。

### 4.3 thinws-ports

只声明 Phase 1 详细设计已经批准且有调用者的 Port；完整名单和职责由该设计维护。后续阶段 Port 是否引入以架构方案为准，不预建空实现。

### 4.4 Adapter

Adapter 负责：

- 系统调用；
- 外部命令；
- 错误码到领域错误的转换；
- 平台能力报告；
- 计划与真实执行结果的证据。

macOS Adapter 承担 Phase 1 详细设计分配给它的平台能力；迁移/接管策略仍由 Core/Application 决定。

Adapter 不负责决定产品阶段、用户权限和业务降级策略。

Adapter 使用跨平台物化设计或对应领域 Port 定义的结构化证据类型，不在技术栈另建平行状态枚举。

## 五、核心库选择

| 能力 | 推荐 crate/方式 | 选型边界 |
|---|---|---|
| CLI | `clap` derive | 实现用户手册冻结的命令与 help 契约 |
| 序列化 | `serde`、`serde_json` | 实现用户手册冻结的 JSON schema |
| 配置 | `serde`＋`toml` | 配置文件版本化；未知关键字段默认报错 |
| 平台用户目录 | `directories` | 实现详细设计冻结的 bootstrap 位置 |
| 领域错误 | `thiserror` | library crate 使用结构化错误 |
| CLI 错误上下文 | `anyhow` | 仅限二进制边界；不能把字符串错误传回 core |
| SQLite | `rusqlite`，启用 bundled SQLite | 同一版本行为可控；同步 CLI 不引入 SQLx/Tokio |
| 日志与诊断 | `tracing`、`tracing-subscriber` | stderr 诊断及同步持久文件输出；强制清理事件不得被日志级别过滤，字段遵守开发规范，不新增审计服务 |
| 实体/操作 ID | `uuid` 的 UUIDv7 | 公开格式以用户手册为准，内部类型以详细设计为准 |
| 本地内容摘要 | `blake3` | 用于本次目录 manifest 与物化证据，不定义 Git BaseKey/BaseId |
| 时间 | `time` | 数据库存 UTC；人类输出按本机时区格式化 |
| 目录清单 | `walkdir` | 仅用于只读清单和非安全关键扫描；clone/delete 使用 dirfd-relative 受控遍历 |
| 临时资源 | `tempfile` | 通过受控目录工厂创建，不直接使用默认系统临时目录 |
| Unix 文件描述符与本机锁 | `rustix` | 按需封装 dirfd、非阻塞 IO 和 advisory lock；不为用户命令引入进程托管框架 |
| macOS FFI | `libc`＋小型自有封装 | `openat/fstatat/readlinkat/symlinkat/fclonefileat` 和 libproc 外部进程探测集中在 macOS Adapter |
| Git | `std::process::Command` 调用系统 Git | 参数数组传递，不经 shell 拼接 |

Phase 1 不再同时引入 `nix`。若 `fclonefileat` 没有现成安全封装，则在 `thinws-adapter-macos` 内建立最小 FFI 层。

### 5.1 暂不采用

Phase 1 不采用：

- Tokio/async-std；
- Axum/Actix Web；
- gRPC；
- Redis/PostgreSQL；
- libgit2/gix 作为 Git 主实现；
- containerd/Kubernetes；
- 自研 Sandbox；
- 动态插件系统；
- 通用工作流引擎。

## 六、macOS/APFS 技术落点

本节只选择 API 和封装位置；Probe、同卷、回执、降级和回滚语义由[《跨平台工作区物化设计》](../design/ThinWorkspace_跨平台工作区物化设计_v1.0.md)管理。

| 实现点 | 选择 | 封装位置 |
|---|---|---|
| 目录和文件身份 | `openat/fstatat/fstatfs` | `thinws-adapter-macos` 的 safe wrapper |
| APFS Volume UUID | 卷属性 API＋`fstatfs` | `MacFileSystemIdentity` 封装 |
| 普通文件克隆 | `fclonefileat(..., CLONE_NOFOLLOW_ANY)` | `ApfsCloneMaterializer` |
| 符号链接 | `readlinkat/symlinkat` | 与克隆遍历共用的 no-follow 封装 |
| 普通文件/目录 mtime | FD 时间属性 API（如 `futimens`） | 同一 macOS 小型封装，保真范围由物化设计定义，须补真实机测试 |
| 外部进程探测 | libproc | 独立小型 FFI 模块 |

Phase 1 不同时引入 `nix` 来封装同一组能力，避免 `libc` 和 `nix` 并存导致文件描述符所有权模型分裂。若稳定 Rust API 无法覆盖所需调用，使用 `libc` 加自有最小 FFI。

`unsafe` 的允许范围、注释和评审要求以《开发规范》为准。平台 FFI 封装对外只暴露安全 Rust 类型，并明确指针/C 字符串生命周期、FD 所有权、errno 读取时机和线程安全不变量。

`cp -c` 不作为能力证据，因为命令行工具的降级行为不属于平台 Receipt 契约。

## 七、Git 只读检查选型

GitInspector 使用系统 Git，具体发现/报告语义以[Phase 1 详细设计 §6](../design/ThinWorkspace_Phase1单机CLI详细设计_v1.0.md)为准。没有 clone/fetch/checkout、read-tree、update-ref、worktree attach/detach、commit/push/PR，也没有 BaseKey 编码或 checkout policy。

- 通过 argv、明确 cwd、验证过的 Git 元数据位置调用，不通过 shell，不让 Git 向父目录发现无关仓库。
- 固定 `LC_ALL=C`，关闭 pager、颜色、外部 diff/textconv、hook、fsmonitor 和 optional locks；清除继承的 Git 路径/仓库选择环境，不能让调用者的 `GIT_DIR` 等改变检测范围。
- 已验证仓库的状态入口为 `git --no-optional-locks status --porcelain=v2 -z --untracked-files=no --ignore-submodules=untracked`，另行逐个检查发现的子仓库；不能让父仓库设置隐藏已跟踪的子模块修改。该命令可能递归访问子模块，因此必须先完成它可能访问的全部子仓库的路径与外部程序安全预检，再调用父仓库 status；做不到则该查询直接 unknown，不能先访问后验证。
- 解析稳定 NUL 输出，处理暂存/未暂存、冲突和 gitlink，保留真实退出结果；不解析本地化文本，也不自行实现 Git 索引或属性转换。
- 不执行仓库或用户配置的外部过滤器。按下方配置边界区分“仅配置了驱动”与“查询需要转换”；不能安全取得结果时报告 unknown，不恢复旧的属性兼容矩阵，不将禁用转换后的结果冒称精确 clean。
- 不能通过更改 index flags、配置、safe.directory 或 refresh 写入来获得结果。sparse/assume-unchanged/skip-worktree 等可能隐藏修改的状态需要验证；无法完整检查时报告 unknown，不修改它们或禁止目录镜像。
- partial-clone/promisor 可能因缺失对象触发隐式 lazy fetch；首版查询前遇此配置即报告 unknown，不以“未主动调用 fetch”冒充不联网，也不为状态检查下载对象。
- 所有内部调用的等待和输出有界；错误由既有结构化结果向上报告。精确超时、输出限额及相应测试在实施任务中冻结，不扩展通用执行器。

配置兼容边界（针对上述固定只读查询；未列出的既有检查不因此放宽）：

| 配置或输入 | 处理与理由 |
|---|---|
| `core.excludesfile` | 允许；忽略规则不隐藏已跟踪内容，固定查询不枚举未跟踪文件 |
| `core.longpaths` | 允许；这是路径能力设置，不是隐藏 tracked 修改或执行外部程序的开关；不据此承诺 Windows 支持 |
| `status.showUntrackedFiles` | 允许；固定命令的 `--untracked-files=no` 覆盖该展示设置，不放开整个 `status.*` |
| 非空驱动名下的 `filter.<driver>.clean/smudge/process/required` | 允许已识别的配置形状，但状态查询须施加下述命令级保护；仅安装了 LFS 风格配置不能单独导致 unknown。未知 filter 配置形状仍拒绝 |
| 预检可见的 `filter` 属性 | 继续报告 unknown；首版不证明属性是否实际命中，也不实现索引属性解析 |
| include、可能触发 lazy fetch 的 partial-clone/promisor、未确认安全的执行或隐藏状态配置 | 维持拒绝；不清空用户配置、不修改 index/config 来绕过检查。`.gitmodules` 不是驱动配置来源，不因上述 filter 放宽而接受它提供的驱动配置 |

过滤器保护仅作用于本次命令：按 Git 实际驱动名保留子节大小写和原始字节，将该驱动的 `clean`、`process` 置空并强制 `required=true`，使用既有命令环境配置传递，不拼接 shell 或任意 `-c key=value`。需要过滤转换时必须使查询失败并上报 unknown，不能以可选过滤器直通的结果宣称 clean。配置解析失败和 Git 非零退出仍按原有结构化错误报告；“允许键”不表示保证所有值有效。依据见 [Git 配置键规范化实现](https://github.com/git/git/blob/v2.39.5/config.c#L508-L571)及[过滤器实现](https://github.com/git/git/blob/v2.39.5/convert.c#L927-L995)。

父仓库 status 可能递归查询子模块，保护集合必须覆盖当前仓库及已发现后代仓库的驱动，并在查询前后重验参与仓库的既有证据；继续保留从叶子开始检查及后代 unknown 向上传播。命令环境在子模块查询中的传递须有真实 Git 验收，不能只测独立子仓库。共享保护可能让原本未配置某个同名驱动、但含隐藏索引属性的另一仓库保守返回 unknown；接受此边界，不为消除此类拒绝增加属性解析或另一套查询。预检与重验不是原子快照，也不对抗恶意同 UID 并发替换。依据见 [Git 子仓库环境传递](https://github.com/git/git/blob/v2.39.5/run-command.c#L1711-L1721)。

技术依据：[Git status（含后台 index 刷新说明）](https://git-scm.com/docs/git-status)、[Git 仓库布局](https://git-scm.com/docs/gitrepository-layout)、[Git partial clone](https://git-scm.com/docs/partial-clone)。配置原语实测与完整 Inspector 验收分开记录在对应 Issue/PR；LFS 风格配置测试不等于实际 Git LFS 工具链兼容认证。选型不等于新 Git 检查范围已在 Apple Git 上验证，真实验收按实施计划安排。

## 八、SQLite 与本机锁技术落点

`rusqlite` 使用固定 SQLite 版本，migration 随二进制发布并在事务中升级。连接默认启用：

```text
journal_mode = WAL
synchronous = FULL
foreign_keys = ON
busy_timeout = 有界等待
```

表、约束、operation/Receipt 和 tombstone 语义由[《Phase 1 单机 CLI 详细设计》](../design/ThinWorkspace_Phase1单机CLI详细设计_v1.0.md)与 schema ADR 管理。《技术栈》不维护第二份字段或唯一约束清单。

LifecycleLock 基于 OS advisory lock，通过 `rustix`/小型平台封装实现 bootstrap 和 data-root 两个 scope。锁文件中的 PID 只作诊断，不是正确性依据；SQLite busy timeout 不代替 OS 锁。哪些用例取哪个锁由 Phase 1 详细设计决定，等待时限和公开错误码由用户手册决定。

## 九、CLI 技术落点

CLI 使用 `clap` derive 建模子命令、参数互斥和值解析，使用 `serde/serde_json` 生成版本化输出。公开命令、名称/ID 格式、stdout/stderr、JSON 成功矩阵和错误码只由 [Phase 1 用户操作手册](ThinWorkspace_Phase1用户操作手册_v1.0.md)管理。

为使参数错误也满足公开 JSON 契约，入口在调用 `clap::try_parse` 前只做一次最小的平台侧 JSON 模式预扫描；它不解析业务参数，遇到 `--` 停止扫描，之后的文本不作为选项解释。预扫描结果只选择错误 renderer，不改变 clap 是否接受命令，也不把任何参数转交用户子命令。

## 十、内部子进程与外部占用探测

GitInspector 使用 `std::process::Command` 或小型安全封装传递 argv，不经 shell。对内部 Git 调用保留超时、输出收集和清理证据；不能因直接子进程已退出就假定输出管道一定关闭。具体实现应局部、有界，不扩展为用户命令执行服务。

macOS Adapter 通过 libproc 实现当前用户可见进程的 cwd/open-vnode 尽力探测，经 ProcessProbe 返回结构化证据。Port 职责、进程身份与占用三态由[《Phase 1 单机 CLI 详细设计》](../design/ThinWorkspace_Phase1单机CLI详细设计_v1.0.md)管理，公开删除行为由用户手册管理。

内部子进程清理与外部只读占用探测是不同责任；后者不建立托管进程组，也不向用户工具发送终止信号。

## 十一、测试技术栈

| SQLite 测试 | `tempfile` 下的临时数据库 | 使用与生产相同的 SQLite 构建 |
| Git 集成测试 | 系统 Git＋临时真实仓库 | 不使用 Git mock 替代语义验证 |

| 端到端测试 | release 二进制 | 黑盒运行公开 CLI |
| 变异测试 | `cargo-mutants` | 目标由开发规范确定，时机由任务流程确定 |
| 模糊测试 | `cargo-fuzz`＋`libFuzzer` | harness 目标由开发规范确定，时机由任务流程确定 |

测试不得只 mock Git 和文件系统。Phase 0 / Phase 1 的关键正确性必须在真实 Git 和真实 APFS 上验证。

### 11.1 变异测试

`cargo-mutants` 用于衡量现有测试能否杀死实现变异。测试对象、存活变异处置和执行时机分别由《开发规范》和《任务流程》管理；工具版本及允许的精确排除项保存在 `.cargo/mutants.toml` 和 CI 工具清单。

典型命令：

```bash
cargo mutants --workspace --in-place
```

`cargo-mutants` 版本由 CI 工具清单固定。`--in-place` 只允许在独立 Workspace 和独立 `CARGO_TARGET_DIR` 中运行。

当前质量工具的固定版本清单为 [`tools/quality-tools.toml`](../../../tools/quality-tools.toml)，同时记录 `cargo-fuzz` 与 fuzz nightly；CI 和本地专项验证使用该清单中的版本。

### 11.2 模糊测试

`cargo-fuzz` 调用 libFuzzer。由于 sanitizer 构建需要 nightly，项目默认编译仍使用固定 stable，fuzz 命令显式选择固定日期的 nightly：

```bash
cargo +nightly-YYYY-MM-DD fuzz build
cargo +nightly-YYYY-MM-DD fuzz run <target> -- -max_total_time=<budget-seconds>
```

约束：

- 优先 fuzz 纯函数、解析器和内存模型；
- 需要访问文件系统时，只能使用每次运行创建的受控临时数据根；
- 禁止让 fuzz 输入直接决定绝对路径、删除目标、Git 仓库外路径或 shell 命令；
- `fuzz/artifacts/` 不提交；发现崩溃样本（crash）后先最小化输入，再把稳定复现样本加入回归语料库 `fuzz/corpus/<target>/`，并补普通回归测试；
- 回归语料库（corpus）不得包含源码、凭证、用户绝对路径或其他敏感数据。

## 十二、质量与供应链工具

提交前与收口时的完整命令只由《任务流程》管理。CI 使用本节选定的工具，并增加：

- `cargo deny check`：许可证、重复依赖和禁止来源；
- `cargo audit`：已知漏洞；
- 按《任务流程》触发的 `cargo-mutants` job；
- 按《任务流程》预算运行的 fuzz build/run job；
- APFS 专用集成测试；
- CLI JSON fixture 兼容检查；
- release profile 构建。

依赖规则：

- 新增直接依赖必须在 PR 中说明用途和替代方案；
- 禁止未锁定的 Git dependency；
- 禁止从任意分支拉取依赖；
- `cargo-mutants`、`cargo-fuzz` 和 fuzz nightly 版本必须固定，升级使用独立任务；
- 优先小而稳定的 crate；
- 不为一两个简单函数引入大型依赖；
- `Cargo.lock` 变更必须进入评审。

## 十三、构建与发布

Phase 1 首发验收目标：

```text
aarch64-apple-darwin
```

兼容目标按实际用户需求增加：

```text
x86_64-apple-darwin
```

增加兼容目标或降低 macOS/Git 最低版本前，必须补齐该组合的 bootstrap、`fclonefileat`、只读 Git/子仓库检查、外部占用探测和端到端真实机验证；仅能编译不算支持。

发布产物至少包含：

- `thinws` 可执行文件；
- SHA-256 校验值；
- 版本和 commit 信息；
- 用户操作手册；
- 支持矩阵和已知限制。

对外分发时完成 macOS code signing 和 notarization。内部 Phase 0 构建可以暂不公证，但不能把未公证产物标记成正式 Phase 1 Release。

## 十四、后续阶段选型规则

后续阶段的产品进入条件和新增概念以架构演进方案为准。只有当某阶段已批准引入网络 I/O、本地 daemon、远程 Worker 或 Windows 节点时，《技术栈》才在对应任务中选择 RPC、异步运行时、CAS、数据库或 ReFS API。不因为路线图出现了未来能力，就在 Phase 1 预先增加依赖或 crate。
