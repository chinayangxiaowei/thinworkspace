# 开发规范

**适用范围：ThinWorkspace**

**当前强制阶段：P0 / P1｜语言：Rust**

本文作为研发执行规范，沿用标准阶段简写：`P0` 对应设计文档的 `Phase 0（关键技术验证）`，`P1` 对应 `Phase 1（单机 CLI MVP）`；后续阶段同理。

---

## 一、规范目标

本规范用于保证以下性质不会因为多人或多 Agent 并行开发而退化：

- 平台层与领域层边界清晰；
- 不同文件系统能力不会被误报；
- 创建与删除不把未完成状态冒充成功；显式清理只作用于受控目录；
- 已声明支持的 Git 检查只读且不伪造完整性，不把文件副本误称为外部引用隔离；
- CLI、JSON 和错误码对用户保持稳定；
- 文件和分支不会被未经确认地破坏；
- P1 不提前引入 P2–P5 的概念和复杂度。

本规范中的“必须”“禁止”是合并门禁，不是建议。

---

## 二、最高优先级原则

### 2.1 不伪造能力

预检、计划、真实执行结果和保证强度是不同事实。实现不得静默降级，不得把 API 存在、文件系统名称或预检成功写成 confirmed。完整语义模型以《跨平台工作区物化设计》为准。

### 2.2 状态不由目录外观推断

目录存在不等于对象可用。代码必须通过领域状态、Receipt 和当前外部事实共同判定，不得在查询路径中隐式修改状态。

### 2.3 依赖向内

Core/Application 不按操作系统名称分支，不直接调用 SQLite、Git CLI 或系统 API。平台差异收敛在 Adapter，产品策略留在 Core/Application。

### 2.4 安全失败

无法证明能否覆盖、删除、迁移或降级时，默认停止并保留数据。不得自动增加强制参数或忽略错误以追求流程“成功”。

---

## 三、阶段边界

开发规范不复制阶段能力表。P0/P1 可以实施什么、何时引入后续对象，以《产品与架构演进方案》的“阶段、能力与边界控制表”为准。

任务超出当前阶段时，先停止实施并更新阶段方案/ADR；不得以“先把接口留好”为理由创建没有当前调用者的抽象。

---

## 四、代码组织和依赖方向

允许依赖：

```text
cli → application → core
                  → ports

adapter → ports
        → core data types
```

禁止依赖：

```text
core → adapter
core → sqlite/git/process
ports → concrete adapter
adapter A → adapter B
```

规则：

1. 一个模块只有一个主要职责。
2. 领域对象放 core，流程编排放 application，IO 放 adapter。
3. CLI 不直接执行 SQL、Git 或文件系统系统调用。
4. Adapter 不决定是否允许 Full Copy；它只报告能力和执行结果。
5. 跨 crate 类型优先定义在 core/ports，禁止复制相似结构后手工转换。
6. 不为未来阶段建立空 trait、空 crate 或只有一个转发方法的抽象层。

## 五、Rust 编码规范

### 5.1 格式与命名

- 统一使用 rustfmt，不讨论人工对齐风格。
- 类型、trait 使用 `UpperCamelCase`。
- 函数、变量、模块使用 `snake_case`。
- 常量使用 `SCREAMING_SNAKE_CASE`。
- 领域 ID 必须使用新类型，禁止跨层传裸 `String`；内部身份组成以 Phase 1 详细设计为准，编码与哈希选型以《技术栈》为准。
- Workspace 名称使用专用值对象解析，名称与路径推导完全分离；准确语法、幂等行为和错误码只以用户手册为准。
- 源路径证据以 Phase 1 详细设计和物化设计为准，不新增 Git 来源身份或 Base 编码。
- 路径参数使用 `&Path`/`PathBuf`，禁止使用字符串拼路径。
- 时间持久化为 UTC，显示层再转换时区。

### 5.2 可见性

- 默认私有；只在实际跨模块需要时提升为 `pub(crate)` 或 `pub`。
- 公共 trait、结构和错误码必须有 rustdoc。
- 不稳定的内部实现不得因为测试方便而公开。

### 5.3 错误处理

- Core/Port 使用结构化错误；具体错误库以《技术栈》为准。
- CLI 边界可以添加人类上下文，但必须保留底层类型和稳定 error code。
- 禁止以字符串匹配判断错误类型。
- 禁止吞掉 stderr、errno、Git exit status 或 SQLite error code。
- `unwrap()`、`expect()` 只允许在测试或静态不变量处使用，并写明不变量。
- 用户输入、磁盘、Git、SQLite 和系统调用路径禁止 panic。

结构化错误必须携带类型化错误码、安全的人类消息、可脱敏上下文和可选修复建议；具体数据类型在 Core 实现中定义，公开序列化只以用户手册为准。

### 5.4 unsafe

Core、Application、CLI：

```rust
#![forbid(unsafe_code)]
```

unsafe 只允许出现在平台 FFI 封装中，并满足：

- 一个函数只封装一个明确系统能力；
- unsafe block 前有 `SAFETY:` 注释；
- 输入先在安全 Rust 层验证；
- errno 在下一次可能覆盖它的调用前读取；
- 文件描述符所有权明确；
- 有真实平台集成测试；
- 必须由熟悉平台 API 的 Reviewer 审核，当前在本地完成。

### 5.5 注释

注释解释“为什么”和“不变量”，不重复代码行为。

以下情况必须有注释：

- crash consistency 顺序；
- Git 与文件系统操作顺序；
- 跨卷判断；
- 路径和符号链接安全；
- unsafe 前提；
- 看似可以简化但实际不能改变的代码。

## 六、接口设计规范

1. Port 必须窄：一个接口只表达一类外部能力，不把物化、Git、元数据、进程和观察塞进同一个 trait。
2. Probe 只读事实，Plan 只表达策略结果，Execute 只执行已重验计划，Receipt 只记录真实结果。
3. Adapter 不自行决定产品 fallback、阶段或用户权限。
4. 返回类型必须能区分 unsupported、unknown、partial 和 failed，不用 `bool` 代替证据强度。
5. 失败可能留下外部状态时，错误必须携带剩余范围的诊断上下文或 partial receipt，不承诺自动恢复。
6. 接口类型不泄漏具体 Adapter 的路径格式、errno、SQLite row 或 Git 文本输出。

完整 Port 列表、Phase 1 领域语义和物化数据模型分别以《Phase 1 单机 CLI 详细设计》和《跨平台工作区物化设计》为准。

---

## 七、文件系统规范

- 创建源可接收用户绝对路径并按物化设计验证；受控目标和删除范围必须从已验证 root 与类型 ID 推导，禁止 `..` 逃逸或未验证环境变量。
- 安全关键遍历、创建和删除使用 dirfd-relative/no-follow 方式，防止 canonicalize 之后的 TOCTOU 和 symlink 替换。
- 设备文件、FIFO、socket 和未知特殊类型默认拒绝；保留名称不能被来源树覆盖。
- 破坏性操作前重新核对路径身份、对象归属和领域状态；禁止对空路径、根目录、用户主目录、data root 或未登记路径做递归删除。
- 禁止使用 shell、glob 或命令替换确定删除范围。

data root 布局和生命周期以《Phase 1 单机 CLI 详细设计》为准；APFS、符号链接、跨卷、克隆和回滚以《跨平台工作区物化设计》为准。本规范不复制具体系统调用序列和 errno 策略。

---

## 八、Git 操作规范

- 通过 argv 数组调用 Git，不使用 `sh -c` 拼接。
- 每个调用设置明确 cwd、有界超时和命令级配置，分开捕获 stdout/stderr 并检查 exit status。
- 平台解析使用稳定 locale 和机器可读格式，不解析本地化人类文本。
- 平台命令不修改用户全局 Git config，不隐式执行 hook、external diff/textconv、fsmonitor 或来源仓库定义的未批准程序。
- 凭据只交给 Git credential helper/SSH agent，不记录扩展后 URL 或凭据输出。
- 产品 GitInspector 只读；不得以创建或清理为理由执行 ref/index/config 写入、自动提交、推送或 PR。用户或 Agent 的外部 Git 操作由任务流程管理。

仓库发现、已跟踪检查和外部引用边界由《Phase 1 单机 CLI 详细设计》管理；具体只读命令和配置覆盖由《技术栈》管理。不维护旧托管拓扑或提交可达性保护实现。

---

## 九、状态机与失败边界规范

- 状态迁移只能由 Core 定义的迁移函数完成，不在 Adapter、SQL 调用点或 CLI renderer 中散落判断。
- 外部写入前保存非 Ready 过渡状态；完整物化并验证后才保存最终 Receipt 和 Ready。清理日志的 OperationId 仅关联单次尝试，不构成持久重放意图。
- 每个外部步骤失败时保留可解释状态；进程内回滚可验证，跨进程不承诺重放或补偿。
- 失败不得直接写回旧状态来隐藏已发生的外部事实；Error 不触发自动删除。
- 普通查询只读；不提供 repair/重放用例。未完成目录只能由用户再次显式授权强制清理。
- 测试必须验证未完成状态不成为 Ready、不报删除成功，且显式清理不越出登记范围。

状态值、迁移表、创建/删除顺序和 tombstone 语义只由《Phase 1 单机 CLI 详细设计》管理。

---

## 十、SQLite 规范

- schema migration 单向、版本化，并在空库和每个受支持旧版本上测试。
- 启用 foreign keys，对身份、枚举、唯一性和引用关系使用数据库约束，不用“先查再写”代替并发正确性。
- 写事务保持短小，不在事务内等待 Git、大型文件操作或子进程。
- 查询显式排序，时间统一保存 UTC，ID 通过新类型稳定序列化。
- 不保存密钥、凭据、源码正文、patch 或构建日志。
- SQLite busy timeout 不是 lifecycle OS lock 的替代品。

表/关系不变量和最终 Receipt 语义以《Phase 1 单机 CLI 详细设计》为准；pragma、库和锁实现以《技术栈》为准。

---

## 十一、CLI 与兼容规范

- CLI renderer 不包含业务判断；Application 返回结构化结果，人类输出和 JSON 是两个显式 renderer。
- 稳定状态、错误码和 JSON 枚举使用非本地化稳定值；自然语言 message 不是机器契约。
- 参数错误不得绕过统一错误 renderer。
- JSON 字段删除、改名或语义变化必须通过 schema version 演进。
- 破坏性参数只解除自己明确命名的一项保护，不设计全局 `--unsafe`。
- 实现变更公开行为时，先更新用户手册，再同步 `--help`、fixture 和契约测试；不向架构或本规范复制命令矩阵。

命令、stdout/stderr、JSON、错误码、退出码和各强制参数的准确语义只以 Phase 1 用户操作手册为准。

---

## 十二、内部子进程与外部占用规范

- 平台内部子进程直接执行已批准的 argv，不经 shell，不接收任意用户命令作为 executable。
- cwd 必须是当前操作已验证的范围内目录，不通过 Git 自动上溯到未知父仓库。启动、运行和终止使用结构化结果，不从日志文本反推状态。
- 内部子进程等待、输出收集和清理必须有明确边界；超时不能只覆盖等待退出而遗漏管道读取。清理结果如实区分已确认与未确认事实。
- 不持久化或回显完整 argv/环境；内部凭据处理继续遵循 Git 与日志规范。
- 外部占用证据不得只依赖可能被复用的 PID；探测不授权平台终止用户进程。
- 外部进程探测是尽力能力，不得把未取得证据表述成绝对无占用。
- 工作区不是 Sandbox，不能把用户直接执行的工具描述为受平台隔离或托管。

外部占用职责与删除失败边界以《Phase 1 单机 CLI 详细设计》为准；系统 API 以《技术栈》为准；公开删除行为和错误码以用户手册为准。

## 十三、日志与可观测性

使用结构化 `tracing` 字段：

```text
operation_id
workspace_id
adapter
requested_mode
effective_planned_mode
actual_mode
filesystem_id
git_exit
duration_ms
error_code
```

禁止记录：

- 源码正文；
- patch 全文；
- SSH key；
- access token；
- 完整 credential URL；
- 未脱敏环境变量。

日志消息用于人读，字段用于诊断；不能依赖日志反推唯一业务状态。

### 13.1 清理异常的最小持久日志

复用普通日志设施，不新增审计服务、独立事件库、理由审批或提交证明机制。持久位置与生命周期顺序由详细设计管理，用户查看位置由手册公开。

清理拒绝、Git 检查不完整、外部占用扫描不完整及每次显式强制清理均记录。字段为 UTC 时间、operation_id、workspace_id、事件（refused/started/completed/failed）、force 标记、检查完整性、仓库相对位置与已跟踪变更数量（未知为 null）、保护原因及最终错误/结果。成功 force 即使未发现 dirty 也不能漏记。

强制清理开始事件须在破坏性步骤前同步持久化，结果随后追加；中断缺少完成事件不能伪造成功。日志写入失败如实报告，执行边界按详细设计处理；不得因用户降低日志级别或采用 JSON 输出而过滤掉强制事件。重新显式清理生成新的 operation_id，不重放旧尝试。

不记录未跟踪文件清单、源码、patch、完整 argv/环境或凭据 URL；相对位置需转义控制字符，避免日志注入。日志保留在工作区之外，不随其清理；普通本机日志不宣称不可篡改，也不能代替 commit 验收。

## 十四、测试规范

### 14.1 每个变更的最低测试

| 变更类型 | 必须测试 |
|---|---|
| Core 规则 | 单元测试＋边界测试 |
| 状态机 | 合法/非法迁移＋重复执行 |
| CLI | 成功、参数错误、JSON envelope、逐命令支持矩阵、退出码 |
| Git | 真实临时仓库集成测试 |
| SQLite | 迁移、事务失败、锁超时 |
| APFS | 真实 clone、跨卷、失败回滚 |
| 删除/GC | tracked/unknown 普通拒绝、显式 force 与日志、路径保护、重复删除和 GC 范围 |
| unsafe/FFI | 平台测试＋错误码覆盖 |
| Core 状态、策略或安全判断 | 对变更模块运行 `cargo-mutants`；关键存活变异必须处理 |
| 路径、名称、Git/JSON 解析或状态序列 | 对受影响的模糊测试目标运行有界 smoke test |

### 14.2 故障注入点

生命周期用例必须从对应详细设计提取故障点，覆盖非 Ready 状态写入、外部副作用中途失败、最终发布前及进程内补偿失败。测试目标不是“没有错误”，而是错误后状态可解释、不误报成功，显式整目录清理不破坏其他 Workspace；不要求跨进程续做或重放。本规范不维护第二份创建/删除步骤表。

### 14.3 变异测试与模糊测试

- 状态机、降级、删除保护、强制边界、日志遗漏和错误映射的行为变化必须运行变异测试。
- 存活变异（surviving mutant）必须补测试或给出经过 Reviewer 接受的等价变异说明，不能只提高全局变异得分。
- 外部字节流、路径组件、名称、Git 输出、JSON 和状态转换序列必须有对应模糊测试目标。
- 模糊测试目标不得对任意绝对路径、真实用户仓库或非临时数据根执行写入和删除。
- 模糊测试崩溃样本必须最小化并转成语料库样本和普通回归测试；修复前不得删除失败 artifact 来使 CI 通过。
- 变异测试、模糊测试工具及 fuzz nightly toolchain 必须固定版本。

### 14.4 提交前命令

提交前命令及其执行时机只由《任务流程》的“通用门禁”和“三级门禁”管理。涉及 APFS、Git 生命周期或删除的变更，还必须按对应详细设计和任务专项门禁在真实 APFS 集成环境运行适用测试。

## 十五、代码评审规范

本地变更的审核说明必须包含：

```text
目标
阶段归属
范围内
范围外
状态机/数据影响
失败与未完成状态
测试证据
CLI/JSON 兼容影响
安全影响
```

必须请求专项 Reviewer 的情况：

- unsafe/FFI；
- 递归删除；
- Git branch/ref/GC；
- SQLite schema migration；
- 状态机变化；
- JSON schema 或错误码变化；
- 降级策略；
- 命令执行和环境变量。

评审不能只看 happy path，必须追问：

1. 中途 kill 会留下什么？
2. 未完成状态是否会误报成功，显式清理是否限于登记范围？
3. 路径或卷变化会怎样？
4. 是否可能静默 Full Copy？
5. 是否可能删除未保护数据？
6. stdout/JSON 是否仍兼容？

## 十六、ADR 与文档规范

以下变化必须先写 ADR：

- Git 检查职责或外部引用边界；
- 物化输入与内容身份语义；
- SQLite schema 主模型；
- APFS clone 实现方式；
- fallback 默认策略；
- 状态机增加或改变；
- 引入 async runtime、daemon 或网络协议；
- 新平台正式支持；
- 安全边界变化。

ADR 至少包含：背景、决策、备选方案、代价、迁移方式和验证计划。

用户可见命令变化必须修改唯一公开契约并同步其可执行证据：

- P1 用户操作手册；
- `--help`；
- JSON fixture；
- 任务验收标准。

只有该变更同时改变阶段边界或内部设计时，才修改架构方案或详细设计；不得仅为“保持同步”复制命令表、错误码表或 JSON 字段。

## 十七、完成定义

任务何时可标记 Done、小阶段何时可收口、阶段何时可放行，只由《任务流程》管理。本规范只定义实现必须满足的工程规则和应产生的测试证据，不维护第二份 Done 清单。

---

## 十八、明确禁止事项

- 绕过 Core/Port/Adapter 边界，把产品策略分散到 CLI、SQL 或平台调用点。
- 绕过类型状态、最终 Receipt 或路径归属校验直接修改/删除外部对象。
- 使用 shell/glob/未验证输入决定 Git、文件系统或进程的破坏性范围。
- 为通过门禁而降低阈值、禁用测试、忽略存活变异或丢弃未固化的 fuzz crash。
- 在未更新阶段方案和详细设计前实现未来阶段能力、平行机制或无调用者抽象。
