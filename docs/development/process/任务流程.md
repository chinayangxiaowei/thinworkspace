# 任务流程

**适用范围：ThinWorkspace 的产品与工程任务**

**当前执行阶段：P0 / P1**

本文作为任务管理规范，沿用标准阶段简写：`P0` 对应设计文档的 `Phase 0（关键技术验证）`，`P1` 对应 `Phase 1（单机 CLI MVP）`；后续阶段同理。

---

## 一、流程目标

任务流程要解决四个问题：

1. 每个任务是否属于当前阶段；
2. 开始开发前是否已经具备明确输入和验收标准；
3. 多人或多 Agent 并行时是否会修改相同核心区域；
4. 完成后是否具备可重复验证、评审和安全合并条件。

基本原则：

> 一个任务对应一个明确结果、一个主要负责人、一个 Workspace 和一个可独立评审的变更集。

### 1.1 三层研发节奏

```text
任务 → 小阶段 → 阶段
```

| 层级 | 含义 | 建议周期 | 完成依据 |
|---|---|---|---|
| 任务 | 一个可独立验证的逻辑变化；可以包含多个单一意图 commit | 数十分钟至半天 | 任务验收断言、任务门禁、Review 和 Verification |
| 小阶段 | 一组共同形成可验收子目标的任务 | 1–3 天 | 小阶段退出条件和收口门禁 |
| 阶段 | P0、P1 等架构阶段 | 由架构方案决定 | 阶段退出控制点、阶段门禁、人工放行和版本 tag |

“小阶段”是研发计划中的任务分组，不是产品领域对象，不进入 CLI、SQLite 或运行时模型。可以使用现有 issue milestone、实施计划分组或 Release PR 表示，不创建平行的流程系统。

第一个任务进入 Ready 前，小阶段必须写明一个可观察子目标、退出条件、包含的任务、负责人和适用门禁；不能把同一阶段内任意一批任务临时称为“小阶段”来绕过收口。

测试证据、评审意见和完成声明必须记录在已有任务、PR、CI 或阶段状态载体中。禁止为每次 Agent 工作新建独立审核轮次、交接报告或不参与门禁的流程文档。

本文中的“任务”指项目管理和研发工作项，不是 P4 才引入的产品运行时 `TaskId` 领域对象。任务编号只出现在工单、分支和提交信息中，不进入 P1 产品模型。

## 二、任务状态

```text
Backlog
   ↓
Ready
   ↓
In Progress
   ↓
In Review
   ↓
Verification
   ↓
Done
```

辅助状态：

```text
Blocked
Cancelled
```

| 状态 | 含义 | 进入条件 | 离开条件 |
|---|---|---|---|
| Backlog | 已记录但尚未具备开发条件 | 有目标或问题描述 | 完成范围、依赖和验收梳理 |
| Ready | 可以被领取 | 阶段匹配、输入明确、无未解决阻断依赖 | 负责人和 Workspace 已确定 |
| In Progress | 正在设计、编码或测试 | 任务已领取 | 提交完整、自测通过 |
| In Review | 等待代码/设计评审 | PR 或变更集已创建 | 评审通过或退回修改 |
| Verification | 验证真实平台行为 | 代码评审通过 | 验收场景与故障测试通过 |
| Done | 可交付 | 所有完成定义满足 | 不再修改；新问题建新任务 |
| Blocked | 无法继续 | 外部依赖、决策或环境阻断 | 阻断原因解除并记录 |
| Cancelled | 不再实施 | 需求取消或被替代 | 关闭并说明替代关系 |

本节状态用于单个任务。小阶段收口和阶段放行不复用任务状态机，按第十八节的退出条件和人工放行流程执行。

禁止使用“基本完成”“等以后补测试”等模糊状态代替正式状态。

## 三、任务类型

| 类型 | 用途 | 必须产物 |
|---|---|---|
| Feature | 新增用户或平台能力 | 代码、测试、文档、验收证据 |
| Bug | 修复已知错误 | 复现测试、修复、回归测试 |
| Spike | 验证技术风险 | 实验代码、数据、结论、Go/No-Go |
| ADR | 冻结架构决策 | ADR 文档和验证计划 |
| Refactor | 不改变外部行为的结构调整 | 等价性说明和回归测试 |
| Chore | 工具链、依赖和工程维护 | 影响范围和验证结果 |
| Security | 路径、删除、凭证、执行安全 | 威胁分析、修复和专项评审 |

P0 任务以 Spike/ADR 为主；P1 以 Feature/Bug 为主。

## 四、任务准入

### 4.1 Ready 检查

任务进入 Ready 前必须回答：

```text
目标是什么？
用户或调用者是谁？
属于 P0/P1 的哪项能力？
属于哪个小阶段，该小阶段退出条件是什么？
明确不做什么？
输入和输出是什么？
失败时保留什么状态？
需要修改哪些模块？
与其他任务是否重叠？
验收命令和预期结果是什么？
是否需要真实 APFS/Git 环境？
```

缺少验收条件的任务不能进入 Ready。

### 4.2 阶段边界检查

P1 任务出现以下关键词时默认退回重新评审：

```text
daemon
HTTP/gRPC
Job/Attempt
Worker/Node
Placement/lease
WorkspaceCheckpoint/SourceSnapshot
实时 watcher
Agent 编排
多租户
```

确有必要时，先更新阶段方案或编写 ADR，不能直接在 P1 代码中实现。

### 4.3 风险等级

| 等级 | 范围 | 额外要求 |
|---|---|---|
| R1 | 文档、纯展示、无状态工具 | 普通评审和基础测试 |
| R2 | Core 规则、CLI、JSON | 兼容测试和模块 Reviewer |
| R3 | SQLite、Git、状态机、进程 | 故障注入和专项 Reviewer |
| R4 | unsafe、FFI、递归删除、GC、数据迁移 | ADR/安全评审、真实平台验收、回滚方案 |

任务卡必须标记风险等级。风险由最高影响项决定，不能为了减少流程降低等级。

## 六、任务拆分规则

### 6.1 按可验收结果拆分

推荐按“一个可独立验证的结果”拆分，例如接口契约、一个 Adapter 行为、一个失败边界或一项公开 CLI 行为各自成任务；确有先后依赖时由实施计划表达，不在流程文档预设具体任务序列。

不推荐：

```text
完成整个 Workspace 系统
重构一下平台层
把异常处理补上
```

### 6.2 一个任务一个主要写入区域

P1 尚无实时冲突预警。并行任务应尽量避免同时修改：

- 同一个状态机文件；
- 同一份 SQLite migration；
- 同一个 CLI command enum；
- 同一个公共错误码表；
- 同一个平台 FFI 模块；
- 同一份用户手册章节。

如果无法避免，采用以下优先顺序：

1. 重新切分模块；
2. 先合并公共接口任务，再并行实现；
3. 明确串行顺序；
4. 最后才允许短时间重叠，并指定唯一集成人。

### 6.3 Spike 不能直接变成生产代码

P0 实验代码的目标是验证。进入 P1 前必须：

- 形成结论或 ADR；
- 明确过时实验和证据保留范围；清理须有单独、明确的目标授权，不因路线取消自动删除；
- 按生产接口重新实现或明确评审其质量；
- 补齐错误、失败边界、日志和测试。

## 七、开始任务

### 7.1 领取

任务从 Ready 进入 In Progress 时记录：

- 负责人；
- 协作者/Agent；
- 开始时间；
- 基线 commit；
- 所属小阶段；
- Workspace 名称；
- 预计修改区域；
- 依赖的 ADR。

### 7.2 创建工作区

平台自身可用后，按[用户手册](../../project/reference/ThinWorkspace_Phase1用户操作手册_v1.0.md)从本机原始目录创建工作区。产品不自动新建分支；负责人先核验 Git 元数据是否独立，再按本流程准备任务分支。平台尚不可用时可使用标准 Git worktree，不能把这种研发工具选择当成产品 Git 拓扑。

在现有任务载体记录实际工作区位置、来源、起始 commit/分支及已有修改；只有真实 CoW 证据才能声明 CoW。来源原有未提交内容不能被无意混入本任务提交。外部 Git 指针不能仅因被复制就当成独立仓库；无法安全操作时由主 Agent 决定准备自包含来源，不擅自改写原仓库。

### 7.3 开始前同步

开始编码前检查：

```bash
git status
cargo fmt --all -- --check
cargo test --workspace --all-targets
```

如果基线本身失败，任务不得把失败算作自己的已知问题后继续；应先记录基线故障或调整验收基线。

## 八、任务执行

### 8.1 强制时序

```text
① 对齐 → ② RED → ③ GREEN → ④ 重构 → ⑤ 本地门禁 → ⑥ 自查 → ⑦ 提交
```

| 步骤 | 必须完成 | 退出条件 |
|---|---|---|
| ① 对齐 | 从计划领取任务；写明验收断言、范围外事项、权威文档、状态/数据影响和失败行为 | 没有影响实现的歧义；存在设计缺口时先补设计或转 Blocked |
| ② RED | 先写会失败的单元、契约、属性或集成测试；运行并确认它因预期行为尚未实现而失败 | 测试确实失败，且不是环境、编译或测试自身错误 |
| ③ GREEN | 完成使测试通过的最小实现，同时补齐约定的失败边界 | 新测试与受影响旧测试通过，没有范围外实现 |
| ④ 重构 | 在测试保持通过时消除重复、收紧命名与边界 | 行为不变，依赖方向和安全不变量未被削弱 |
| ⑤ 本地门禁 | 执行通用门禁和本任务专项门禁 | 所有适用门禁通过；未执行项有明确原因且不冒充通过 |
| ⑥ 自查 | 通读完整 diff，对照验收断言、平台红线和文档联动关系 | 无调试残留、无计划外文件、无未说明兼容或安全影响 |
| ⑦ 提交 | 使用 Conventional Commit；一个 commit 只表达一个意图 | commit 可独立理解并关联任务；任务可按逻辑包含多个 commit |

行为变更必须执行 RED。纯文档或无法先写自动化测试的 Chore 可以标记不适用，但必须先定义可失败的检查或明确人工验收断言。

### 8.2 实施中必须维护的信息

负责人持续更新：

- 当前状态；
- 新发现的风险；
- 范围变化；
- 与其他任务的文件重叠；
- 需要的新 ADR；
- 尚未覆盖的故障路径。

发现范围扩张时先停下来拆任务。禁止把“顺手重构”“顺便支持 Linux”“顺便增加 daemon”混入 P1 Feature。

### 8.3 多 Agent 协作

维护者当前要求 P0/P1 由主 Agent 在本机处理，不启动子 Agent。以下并行规则只在维护者重新启用多 Agent 协作后适用。

一个任务可以由多个 Agent 辅助，但必须满足：

- 只有一个最终负责人；
- 每个 Agent 有具体、互不重叠的交付物；
- Agent 不直接同时修改同一关键文件；
- 汇总者检查所有 Agent 的假设和测试；
- 不能以“另一个 Agent 已验证”为理由跳过本任务验收。
- 子 Agent 发现 `AGENTS.md`、权威文档或规则存在错误、矛盾、过期或缺口时，不得自行修改，除非主 Agent 已明确把该文档修正授权为其任务范围；必须先通知主 Agent，由主 Agent 核验并决定不修改、在当前任务修正、另建文档任务或请求用户决策。

通知至少包含：文件和章节、当前表述、错误证据、对当前实现的影响及建议改法。若问题会改变实现、公开契约或安全边界，子 Agent 必须暂停受影响工作；不受影响的工作可以继续。

P1 产品尚无写前预警，因此团队流程必须承担冲突控制。

模型分工按维护者当前要求执行：代码编写可使用 GPT-5.6 Sol（`gpt-5.6-sol`，`xhigh`）；审核必须使用 GPT-6 Astra（`gpt-6-astra`，`xhigh`）。派发时显式设置模型和推理级别，并在既有任务证据中记录实际使用值。审核模型不可用时保留待审核状态并报告，不得用其他模型的自查冒充规定审核。模型分工不替代自动门禁或人工阶段放行。

当前 P0/P1 采用本地提交和本地审核，不要求在线 PR，也不派生专用 PR Agent。主 Agent 保留范围决策、验证证据核对和审核责任；规定审核模型不可用时如实标记待审核，不冒称通过。审核结论绑定精确候选 commit；结果使用现有任务或阶段状态载体，不新增独立审核轮次文件。远端协作仅在维护者重新要求时启用。

每个冻结候选的耗时门禁指定一个执行负责人，不重复启动相同测试。本机与 CI 二选一承担同一范围的变异执行，不因提交或评审再跑一遍。候选变化时按 §18.1 判断证据有效性并补充验证；证据不充分或需诊断失败时可以独立复测，并说明范围与原因。等待和结果读取遵循 §18.4。当前任务验收以本地门禁和真实平台验证为准；阶段放行仍需完整证据与人工确认。

## 九、提交规范

### 9.1 提交粒度

每个 commit 应表达一个可理解的逻辑变化：

- 接口和数据结构；
- 一个 Adapter 实现；
- 一组对应测试；
- 文档同步。

不要求机械地拆成大量微小提交，但禁止把无关格式化、依赖升级和功能修改混成一个 commit。

### 9.2 提交信息

推荐格式：

```text
<type>(<scope>): <summary>

<why / important behavior>

Task: <task-id>
```

类型：

```text
feat fix refactor test docs build chore security
```

示例：

```text
feat(<scope>): <imperative summary>

Explain the reason for the change and its observable result.

Task: <implementation-plan task id>
```

### 9.3 禁止提交

- 密钥和 token；
- 本机绝对路径配置；
- 临时数据库；
- APFS 测试产生的大文件；
- `target/`；
- 用户 Workspace；
- 未说明的大规模格式化；
- 与任务无关的修改。

## 十、自测与门禁

### 10.1 通用门禁

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets
```

### 10.2 任务专项门禁

专项门禁不在流程文档复制每个实现分支的用例。任务根据修改域从其单一设计来源提取验收断言：

| 任务涉及 | 验收断言来源 | 本流程要求的证据 |
|---|---|---|
| CLI 和公开行为 | Phase 1 用户操作手册 | help、fixture、成功/失败契约和退出码测试 |
| 领域、Git、状态机、失败边界、外部占用、GC | Phase 1 单机 CLI 详细设计 | 单元/集成、并发、未完成状态和真实 Git/适用进程证据 |
| Probe、APFS、跨卷、fallback、Receipt | 跨平台工作区物化设计 | 真实文件系统、路径竞态、部分失败和回滚证据 |
| 依赖、FFI、SQLite/Git 命令落点 | 技术栈 | 工具链、供应链、平台封装和错误映射测试 |
| 通用编码与安全规则 | 开发规范 | lint、架构、边界、变异和 fuzz 证据 |

表中的“来源”是读取位置，不是要求再把该文档的矩阵粘贴到任务卡。任务卡只写与本次差异直接相关的可执行断言。

### 10.3 自测报告

进入 In Review 前，在任务或 PR 中记录：

```text
执行命令
运行环境
通过/失败结果
真实 APFS 测试路径
是否做故障注入
变异测试范围与存活变异结论
模糊测试目标、运行预算与新增语料库
未覆盖项及原因
```

只写“测试通过”不算有效证据。

### 10.4 跨域红线自查

涉及对应领域的任务在进入 In Review 前只检查下列跨域问题，细节不在流程中重新定义：

1. 是否仍在当前阶段和任务范围内？
2. 是否可能静默降级、伪造 confirmed 或越过依赖边界？
3. 失败/中断后的外部状态是否可解释，是否避免误报成功或自动续做？
4. 是否有未经验证的路径、删除、Git ref、进程或凭据风险？
5. 公开契约是否仍与用户手册一致？
6. 是否已从命中的详细设计/开发规范提取并执行适用测试？

任一应回答“否”且无已批准的修正方案，均阻止进入 In Review。

## 十一、进入评审

任务进入 In Review 前必须具备：

- 可评审的本地 commit；
- 任务模板信息完整；
- 自测通过；
- 没有未说明的范围变化；
- 文档已同步；
- 无调试代码和临时开关；
- 所有 fallback 都是显式的；
- 状态/数据变化有失败边界说明。

### 11.1 Reviewer 检查顺序

1. 是否符合阶段边界；
2. 是否可能破坏或删除数据；
3. 状态机与未完成状态是否闭合；
4. Probe/Plan/Receipt 是否一致；
5. Git、路径和卷判断是否正确；
6. CLI/JSON 是否兼容；
7. 测试是否覆盖失败路径；
8. 代码结构和可维护性。

先检查正确性和数据安全，再讨论命名和局部风格。

### 11.2 评审结论

| 结论 | 行为 |
|---|---|
| Approve | 进入 Verification |
| Changes requested | 返回 In Progress |
| Blocked by ADR | 转 Blocked，并创建/关联 ADR |
| Out of phase | 返回 Backlog 或调整阶段，不继续合并 |

## 十二、Verification

Verification 使用 release 或接近 release 的二进制，在任务指定的真实目标环境执行其验收断言。

验收集不在本文档硬编码：

- 任务级验收来自任务卡和命中的权威设计；
- 小阶段验收来自《Phase 1 实施计划》对应小阶段的退出条件；
- 阶段验收来自架构方案的阶段边界控制表。

执行时必须使用与变更相关的真实 Git/文件系统/进程环境，并包含适用的失败与未完成状态断言；不要求跨进程续做或重放。未执行项必须记录原因，不得用 mock 结果冒充真实平台验收。

验证失败时任务回到 In Progress。禁止让任务保持 Done 同时新建“以后修”任务掩盖当前验收失败。

---

## 十三、合并与完成

当前 P0/P1 使用本地 Git 提交与本地审核，不以线上 PR 或合并作为任务 Done 的前置条件；远端发布流程须由维护者另行启动。

本地任务完成前：

1. 基于最新目标分支更新或重建验证基线；
2. 解决合并冲突；
3. 重新运行受影响测试；
4. 确认适用的本地门禁和真实平台验证通过；
5. 审核精确 commit；需整合到目标分支时再检查并执行本地合并。

标记 Done 前确认：

- 本地 commit 已完成并经过规定审核；
- 验收证据可访问；
- 文档已发布；
- 相关变异测试和 fuzz smoke test 已通过，或有明确的不适用说明；
- 没有需要人工清理的数据；
- 后续任务已单独登记；
- 任务 Workspace 已删除或明确保留原因。

清理按用户手册执行。产品清理成功不表示任务交付成功；具体交付和主管验收要求只在下节维护。

### 13.1 commit 交付与主管 Agent 验收

对产生仓库改动的任务，完成声明必须提供仓库标识、与来源原分支不同的任务分支、完整 commit OID 及验证结果。各有改动的子仓库分别提供证据；submodule 的父仓库还须交付任务要求的 gitlink 更新。当前不要求线上 PR 或 push；ThinWorkspace 不自动执行这些外部 Git 操作。

主管 Agent 必须能读取 commit 并核对它包含本任务的实际修改，不能接受无关的基线 commit、只有 hash 的口头声明或“工作区已清理”作为成果。新增文件即使不在产品清理提示范围，仍必须按任务验收纳入应交付的 commit；不得把 tracked-only 提示当成遗漏新文件的理由。

负责人或主管须在清理前将成果保存到工作区之外的持久仓库，并从该位置核验 commit 可读取；仅在原副本中看过 commit 不算接收。已复制的原始未提交改动与本任务改动要在对齐和自查中区分，不顺手提交无关内容。

Agent 可以按授权显式强制清理，但强制成功或异常日志均不豁免 commit 交付。没有可核验成果时不能进入 Done，由主管处理未完成任务；不在产品层新增提交证明检查、push/PR 硬门禁或主管审批服务。强制操作记录在产品日志，已有任务/PR 中说明处置即可，不新建异常审核报告。

## 十四、Blocked 流程

任务进入 Blocked 时必须记录：

```text
阻断原因
已经完成的检查
缺少的决策/权限/环境
负责解除阻断的人
下次检查条件
是否影响其他任务
```

常见处理：

| 阻断 | 处理 |
|---|---|
| Git 检查或外部引用边界不确定 | 回到只读证据和既定 unknown 边界，不借机恢复 Git 托管架构 |
| APFS 行为不确定 | 转 P0 Spike，提供最小可重复实验 |
| 阶段外需求 | 返回 Backlog，关联后续阶段 |
| 测试环境缺失 | 建设环境任务，当前任务保持 Blocked |
| 与其他任务重叠 | 重新拆分或规定串行顺序 |

Blocked 不是隐藏开发状态。没有解除条件的 Blocked 任务应重新评估是否取消。

## 十五、Bug 流程

Bug 任务必须先有可重复复现：

```text
环境
命令
输入路径/文件系统
期望结果
实际结果
错误码和诊断
是否涉及数据损失
```

优先级：

| 优先级 | 条件 | 行为 |
|---|---|---|
| Critical | 数据损失、错误删除、跨 Workspace 污染 | 停止发布，立即修复并回归 |
| High | 错误标记 confirmed、静默降级、未完成状态被误报成功或越界清理 | 阻断对应能力发布 |
| Normal | 功能错误但有安全替代路径 | 进入当前迭代 |
| Low | 文案、非关键体验 | 正常排期 |

修复必须增加失败前的复现测试，不能只修改实现。

## 十八、小阶段收口与阶段放行

### 18.1 三级门禁

原则：快测试进入每个任务；日常变异按影响范围执行，全量变异只用于小阶段和阶段收口。低层门禁通过不能替代高层门禁要求的覆盖范围。

| 门禁 | 触发时机 | 最低内容 | 失败处理 |
|---|---|---|---|
| 任务门禁 | 每个逻辑 commit 提交前，以及任务进入 In Review 前 | fmt、Clippy、单元/契约/适用集成测试；适用时运行变更函数/模块及其影响范围的变异测试和受影响 fuzz target 短时 smoke；专项红线 | 不得红着提交或进入评审 |
| 小阶段门禁 | 一个可验收子目标准备完成时 | 全 workspace 普通测试；受影响 crate 的全量变异测试；相关 fuzz target 统一短预算；真实 Git/APFS 场景；该子目标 E2E | 修复明确缺陷并重跑；不能用后续任务替代当前退出条件 |
| 阶段门禁 | P0/P1 放行前 | release 构建；全量变异测试；所有 fuzz target 的记录化长预算；阶段适用的失败边界、性能和真实平台验收；公开契约检查 | 未通过不得人工放行或打 tag |

每次收口必须记录 fuzz 运行预算、平台环境和测试范围。门禁只能加严；跳过、禁用或排除测试必须在既有任务或 Release PR 中写明理由、负责人、影响和失效条件。

变异范围与证据按以下规则执行：

1. 任务对齐时确定受影响的生产函数/模块及理由。调用方、共享策略、测试、fixture、依赖或配置变化也可能扩大范围；仅筛选 diff 行不能证明覆盖了语义影响。缩小变异目标不等于缩小验证它的测试集。
2. 修复失败项时，重跑未解决的变异及修复影响范围；不为得到一份全绿摘要而重启所有无关变异。旧失败结果保留，并关联修复后的证据；未确认等价或未修复的关键存活项仍阻断交付。
3. 未受影响的证据可复用，但必须核对生产代码、相关测试/fixture、依赖、工具及配置、目标平台和运行条件，并绑定原候选及新候选的差异。代码行号移动时核对实际变异位置与操作，不能只比名称。无法证明不受影响的部分重跑，不能把旧候选的整体通过状态直接贴给新候选。
4. 小阶段/阶段必须具备表中完整范围的有效证据，可由仍有效的既有结果与补充执行共同组成；不是每次修复后都无条件重跑全量。收口时由负责人和 Reviewer 核对覆盖缺口。
5. 纯文档变更不运行变异测试。当前本地流程执行适用的普通测试、真实平台、静态检查、供应链及 fuzz 门禁；变异证据由指定执行负责人交付。未来恢复 CI 时须明确执行范围。未执行 CI 须标明“未执行”，不能宣称 CI 已通过；没有有效的本地替代证据仍不能完成任务。

### 18.2 小阶段收口流程

```text
任务完成
    ↓
运行小阶段门禁
    ↓
逐条核对小阶段退出条件
    ↓
修复明确缺陷并增加回归测试
    ↓
重跑受影响测试，按 §18.1 补齐完整小阶段门禁证据
    ↓
在既有计划或 Release PR 中完成声明
```

小阶段完成声明至少记录：子目标、包含的任务/commit、退出条件结果、门禁环境、未执行项和遗留问题。Critical、High 以及影响退出条件的 Normal 缺陷必须为零；其他 Normal/Low 必须有明确处置，不得隐藏为“以后再看”。

### 18.3 阶段放行流程

```text
核对架构阶段退出控制点
    ↓
运行完整阶段门禁
    ↓
执行平台红线与公开契约检查
    ↓
修复阻断缺陷，按 §18.1 补齐完整阶段门禁证据
    ↓
人工确认放行
    ↓
按发布版本策略打 tag
```

人工放行记录至少包含：

- 阶段名称和候选 commit；
- 退出控制点逐项结果；
- 测试环境、命令、变异测试和 fuzz 预算；
- Critical/High 为零的确认；
- 遗留 Normal/Low 和开放边界及处置；
- 确认人、时间和最终 tag。

Agent 可以整理证据和指出缺口，但不能代表人类完成阶段签字。放行记录写入现有 Release PR、milestone 或阶段状态页之一，不再创建独立 Agent 审核报告。

### 18.4 耗时变异的等待与结果读取

- 启动前，在既有任务或 PR 中记录候选、执行负责人、范围、平台、工具配置、并发度、启动时间和结果位置。首次缺少可比历史时，暂按 **1 小时**安排首次主动查看；这是等待估计，不是测试超时或完成承诺。
- 后续参考上一次同类执行的实际耗时，结合本次范围、并发度和平台差异重新估算，并为正常波动留出余量。取消、超时或提前失败的未完成批次不能当作全程耗时；完整跑完但有存活项的时长可以参考，结果仍记为失败。没有可比记录时仍采用暂定值。结束后补记实际耗时，供下一次使用，不新建调度系统或独立等待报告。
- 预计查看时间到达前，执行不修改冻结候选、也不干扰该批次资源的独立工作，或使用工具提供的延后唤醒/完成通知并结束当前等待。不得反复查询进程、读取日志或轮询未变化的进度。完成/失败事件或用户明确要求查看时可以提前处理。
- 到预计时间仍未结束，只做一次状态检查，根据已有进度和耗时重新估算下一次查看时间；不退回固定短间隔轮询。正常运行不重复通知“仍在运行”。
- 完成后先读取退出码、计数和耗时摘要；只有失败、存活变异、超时或证据异常时才读取相关明细。不得把整批原始日志持续灌入模型上下文。
