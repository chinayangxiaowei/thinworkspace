# ADR-0005：Phase 1 暂不实现 GC

**状态：已接受｜范围：Phase 1｜决定：首版保留当前空间统计，不发布 `thinws gc`**

## 职责

记录维护者对首版 GC 范围的决定，以及它与显式 Workspace 清理的边界。

## 非职责

不定义空间扫描算法、`workspace remove` 的删除步骤、未来 GC 候选协议或 CLI 输出；这些分别由 Phase 1 详细设计、既有删除契约和相应阶段的后续设计管理。

## 背景

原 Phase 1 方案承诺受限 GC，只处理已完成操作留下、归属可证且明确标为可回收的 staging/trash 残留。当前实现没有这类持久候选的生产者：失败回执中的相对隔离名和创建身份不是日后自动删除授权；失败的 staging 与部分删除隔离物可能仍属于未完成操作。仅增加一个返回空计划的 `gc` 命令不会交付实际回收能力。要安全实现有效 GC，需另设计候选标记的建立、撤销、持久化与执行前重验，扩大首版生命周期和验收面。

## 决定

1. Phase 1 交付 Ready Workspace 的当前空间统计，以及由用户显式触发的 `workspace remove [--force]`。删除只清理其已登记、归属可证的 Workspace 容器和对应清理隔离位置；日志及 data root 的其他全局 staging/trash 项不随之扫除。
2. Phase 1 不提供 `thinws gc`、GC dry-run、自动回收、后台清理、持久 GC 候选标记或为了日后 GC 预建的 Port/表/状态。未知或仅凭名称可见的全局残留不由产品猜测归属并删除。
3. 进程内已经存在的身份约束回滚与显式强制清理保留；创建或删除中断不自动续做。残留占用空间必须如实作为首版限制呈现，不把 Workspace 当前用量估算冒充可回收字节或成功清理证明。
4. GC 何时进入后续阶段尚未排期。只有出现可验证的候选来源、持久归属与删除授权，并单独更新产品范围、详细设计、公开契约和真实平台门禁后，才能发布 GC；不得用空命令或宽泛的 trash 扫描代替。

## 影响与验证

同步移除 Phase 1 架构、详细设计、用户手册和实施计划中的 GC 交付承诺；P1-13 收敛为空间统计任务。首版端到端验证须确认 `thinws gc` 返回既有 `E_USAGE`，`workspace remove` 仍只删除受控 Workspace 范围，当前空间统计不宣称独占可释放量。后续 GC 不因本决定获得提前实现资格。
